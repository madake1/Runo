# Runo 项目总览与阶段计划

版本：2026-10-21。本文从产品目标、阶段交付到可执行任务逐层展开；研究依据见 [数据集与模型调研](dataset-research.md)，历史结果见 [开发日志](Logs.md)。阶段中的目标是**计划验收标准**，不是已经取得的模型成绩。

## 一、产品目标

让用户拿起普通 Android 手机，在离线相机预览里看到可靠的目标框；定格画面后，能看清目标、结果和不确定性。先做好果实定位，再逐步加入经验证的病害区域与病名。界面不应把“画到了某个区域”解释为“已经确诊”。

第一版核心体验只有三步：**打开相机 → 实时看到框 → 点击定格查看结果**。树木编号、GPS 建档、全树计数、分享至聊天应用和 LLM 问答不列为当前交付条件；日后有明确使用需求再评估。

## 二、发布层级

| 层级 | 用户能做什么 | 前置条件 |
| --- | --- | --- |
| 工程原型 | 在手机上实时看到离线检测框并定格 | 相机、ONNX 推理与绘制链路可运行；**已实现，但误检较多** |
| 果实试用版 | 在目标果园较稳定地定位蜂糖李和青脆李，少把枝叶/其他物体画成李子 | 有真实绿色李子与负样本，独立测试和真机验证通过 |
| 病害试验版 | 对已定义的病叶/病果或病斑显示“疑似异常”；有充分证据时再显示具体病名 | 类别定义、来源可靠的标注、独立测试和不确定结果处理 |
| 可交给家人使用的版本 | 离线使用稳定，提示语易懂，定格结果可复核 | 长时间运行、不同手机与果园场景验证；病害知识资料可追溯 |

## 三、路线图与交付门槛

以下按依赖顺序执行。工作量是**一人兼职开发的粗略估算**，不包含等待果园拍摄季节、专家确认或外部数据授权的时间；每阶段是否结束以交付门槛为准。

| 阶段 | 预计投入 | 主要交付物 | 进入下一阶段的门槛 |
| --- | --- | --- | --- |
| M0：端侧链路 | 已完成 | YOLO11n→ONNX→Android 实时画框与定格，C++/Python/Android 工程分离 | APK 能在真机运行；当前误检作为待解决问题保留 |
| M1：误检定位 | 1–2 周 | 真机误检样本包、桌面/手机同图对照、问题归因记录 | 能说明主要误框发生在预处理、后处理、阈值或模型泛化的哪一环；同图结果可复核 |
| M2：真实果园数据 | 2–4 周起 | 蜂糖李/青脆李/负样本的标签规范、采集清单、按来源隔离的训练与测试集 | 图片、框、品种、来源组抽查合格；测试集未混入同树连拍的训练帧 |
| M3：果实模型迭代 | 2–3 周 | YOLO11n 基线改进与 YOLO26n 同数据对照、ONNX 验证、手机性能报告 | 在独立果园样本上同时报告召回、误框和设备延迟；选择较合适的一版部署 |
| M4：病害任务试验 | 随数据而定 | 病害标签方案、专家核对样本、病害框或分割原型 | 每个要显示的病名有可审查的标注与独立测试；不足则只显示“疑似异常/无法判断” |
| M5：家庭试用与稳定性 | 1–3 周 | 多次实地试用、错误提示、定格结果说明、发布检查单 | 手机连续运行稳定，用户看得懂结果限制，明显错误能够收集并回流 |

M2 和 M4 的时间最不确定：模型训练可以重复，但真实病害发生时间和标签确认无法靠增加训练轮数替代。

## 四、各阶段工作包

### M1｜把“什么都像 plum”查清楚

1. 给调试版加原始帧、模型输出框与分数的保存方式；收集真李子、非李子绿色物体、叶片、空画面、逆光和模糊帧，同时记录手机型号与画面方向。
2. 同一张原图分别走 Python 导出的模型和 Android 预处理/后处理，核对 RGB 通道、旋转、裁剪、缩放填充、输出张量、置信度和 NMS；修正可复现的实现差异。
3. 对剩余误框按场景分组，比较阈值调整与补负样本的效果。保留一组不参与调参的画面，避免在少数示例上“调好看”。

**交付**：对照图、误检分类表、修改前后的同组结果。若端侧与桌面一致而两者都误检，就把重点转到 M2/M3 的数据与模型。

### M2｜建立能代表家里果园的数据

1. 先记录标签定义：一颗果实如何框、遮挡果实是否标、健康与病害怎么区分；病斑、病叶和病果属于不同标注粒度。
2. 采集绿色果实与非目标画面，覆盖距离、光照、遮挡、背景和不同日期；保留原图与来源信息。
3. 按树/日期/视频来源分组划分训练、验证、测试。测试集先封存，只在确定模型方案时评估。
4. 抽查漏标、错标与同图重复；记录数据来源和许可。优先做小批量高质量样本，核对结果后再扩大。

**交付**：版本化的标签规范、数据清单、划分报告与固定测试集。公开 ACFR 可用于初始化和对照，但目标果园的成绩必须单独报告。

### M3｜选出真正适合手机的果实模型

1. 固定数据划分、输入尺寸和评价脚本，先重训现有 YOLO11n；再以相同条件测试 YOLO26n。若更换输出模式，同步更新 Android 解码器并做同图校验。
2. 分开统计果实漏检和非目标误框，查看小果、遮挡、背光等分组表现。根据错误样例补标或补采，不只比较总体 mAP。
3. 在同一部手机上记录模型大小、APK 大小、帧处理时间的中位数与高位值、连续运行和电量/发热感受；达不到体验要求时再试输入尺寸、运行时加速或量化。

**交付**：实验配置、权重与导出协议、桌面/端侧一致性结果、真机比较表和最终选型理由。任何论文或官方基准的速度都不能替代本机实测。

### M4｜病害识别按数据能力逐步打开

1. 与熟悉果园病害的人确认首批目标、器官、病名与易混症状；优先选家里确实出现、可稳定拍到的少量问题。
2. 决定先框“疑似异常区域”、框病叶/病果，还是给病斑做掩码。先用一种统一粒度标注，避免训练标签含义混乱。
3. 对每个病类建立独立测试样本和不确定/健康对照；样本稀少时不向用户输出确定病名。
4. 先试与现有端侧检测协议兼容的轻量模型；只有框无法表达范围时才进入分割与 Android 掩码绘制。

**交付**：病害标签说明、可追溯的样本与评估报告、对“不知道”的明确界面处理。病害识别结果应允许用户继续查阅可靠资料，但资料查询不替代模型验证。

### M5｜从实验应用到家庭试用

1. 调整框与文字在强光、密集目标、暂停画面下的可读性；定格后显示图片与检测结论的来源及局限。
2. 验证相机权限、模型缺失、低光、后台恢复和长时间运行的行为；对性能较弱的普通手机复测。
3. 为明显错误提供保存样例的简单路径，定期回到数据集核对与训练流程。

**交付**：能重复安装、离线使用、问题可追踪的试用包。是否再加入联网资料库或 LLM 入口，由实际试用反馈决定。

## 五、统一验收口径

每次模型实验至少保存：数据版本与来源分组、类别定义、训练配置、权重/ONNX 哈希、桌面指标、真机型号与耗时、典型正确和错误画面。报告应分别给出果实漏检、非目标误框、病害错报/漏报，以及“无法判断”的数量；不要把同一来源的连拍帧当作独立泛化测试。

首轮果实试用版的**讨论用目标**是：独立负样本视频中明显误框尽量控制到每分钟不超过 1 次，同时对可见、未严重遮挡的目标果实保持可接受召回。正式阈值需在 M2 固定测试集与实际使用距离确定后共同定稿；不能通过单独提高阈值让误框变少，却不记录漏检增加。

## 六、现在就做的任务顺序

1. 收集并保存 20–30 个真机误检/正确案例，附框分数和原图。
2. 完成 Python 与 Android 同图、同预处理的逐步对照，修复协议差异。
3. 写一页果实与非目标的标注规范，拍第一批蜂糖李、青脆李和空画面。
4. 固定来源隔离的验证/测试集，得到当前 YOLO11n 的真实基线。
5. 再决定补数据、调模型或比较 YOLO26n；病害标签方案与果园专家确认同步启动。

阶段状态与实测数值持续写入 [开发日志](Logs.md)。计划改变时更新本文的阶段门槛，不把历史实验记录塞回根 README。
